## 2. What the deployment was before

Deploying meant SSHing to the box and running `docker compose up -d --build` inside
a git clone at `/home/ubuntu/agentic-system-frontend`. That single command did
`npm install`, a full Vite production build, a Docker image build, and a container
restart — all on the production host, in the foreground of the deploy.

### The old `Dockerfile`

Already multi-stage and structurally correct (build → static `dist/` → nginx). Its
problems were subtler:

```dockerfile
FROM node:20-alpine AS build
COPY package*.json ./
RUN npm install --no-audit --no-fund   # NOT npm ci
COPY . .
ENV NODE_OPTIONS="--max-old-space-size=2560"
RUN npm run build
```

The `npm install` was deliberate, with a comment explaining that `npm ci` failed —
the lockfile is generated by npm 11 locally, but `node:20-alpine` ships npm 10,
which reads npm 11's optional platform deps (`@esbuild/linux-*`) as missing.

### The old `docker-compose.yml`

```yaml
version: '3.8'          # obsolete in Compose v2, emits a warning
services:
  frontend:
    build:              # ← the whole problem
      context: .
    ports: ["${APP_PORT:-8002}:80"]
```

No `image:`, no healthcheck, no log rotation.

### Measured problems on the host

| Finding | Evidence |
| --- | --- |
| **Heap cap exceeded physical RAM** | `NODE_OPTIONS=--max-old-space-size=2560` on a box with `Mem: 1.9Gi`. Every build swapped hard against 2 GiB of swap. This is the direct cause of "redeploy takes a lot of time." |
| **Disk 99% full** | `/dev/root 19G 19G 257M 99%` |
| **10.72 GB of orphaned Docker layers** | `docker system df` → 186 images, 87% reclaimable. Every on-server build left another orphan set. |
| **47 MB of dead build context** | `AADML_Agentic_UIUX/` was shipped into every build context. Nothing in `index.html`, `src/`, or the Tailwind content globs references it. |
| **Heavy bundle** | `dist/` is 19 MB; the Monaco chunk alone is 4.25 MB. Legitimately expensive to build — which is exactly why it shouldn't happen on a t2.small. |
| **No CI whatsoever** | The repo had no `.github/` directory. Nothing tested the code before it went live. |
| **One failing test** | The suite was 256/257 — a stale assertion nobody had noticed. |

## 3. What was built

### 3.1 Correction to the original plan

The original proposal was written for **Next.js** — `output: "standalone"`,
`CMD ["node","server.js"]`. This app is **Vite + Vue 3**, which compiles to static
files served by nginx. There is no Node server in production, so those parts were
dropped. Everything else (CI build, ECR, immutable SHA tags, `--no-build`) applied
unchanged.

### 3.2 Files changed

| File | Status | Change |
| --- | --- | --- |
| `Dockerfile` | modified | `node:20`→`node:24-alpine`; `npm install`→`npm ci`; dependency install split into its own cache-friendly layer; BuildKit npm cache mount; heap `2560`→`4096` |
| `.dockerignore` | modified | Added `.github`, `AADML_Agentic_UIUX`, `old_design`, `tests`, `scripts`, `*.log`, `.claude`, `.vault`, `Dockerfile*`, `docker-compose*.yml`, `deploy.sh` |
| `docker-compose.yml` | rewritten | Pull-only: `image:` from ECR, **no `build:`**, `container_name`, healthcheck, JSON log rotation, dropped obsolete `version:` |
| `docker-compose.build.yml` | **new** | Local-build override so a build can never start on the prod host by accident |
| `nginx.conf` | modified | Added `location = /healthz` returning `200 "ok"` |
| `deploy.sh` | **new** | ECR login → pull → `up -d --no-build` → health-gate → **auto-rollback** on failure |
| `.github/workflows/build.yml` | **new** | push to `main`: `npm ci` → `npm test` → buildx → ECR. Never touches the server (added in Phase 2, §11) |
| `.github/workflows/deploy.yml` | **new** | `workflow_dispatch` only: SSM → `deploy.sh <tag>` on the box |
| `.gitattributes` | **new** | `*.sh text eol=lf` — a CRLF `deploy.sh` fails on Linux with `bad interpreter: ...^M` |
| `.gitignore` | modified | Added `.deploy.env` (**not** matched by the existing `.env` / `.env.*` patterns) |
| `DEPLOY.md` | **new** | Setup + runbook |
| `src/composables/useAgentTimeline.test.js` | modified | Fixed the stale assertion (see §4.2) |

### 3.3 Why `node:24-alpine` specifically

Node 24 ships **npm 11**, matching the npm that generated `package-lock.json`
(lockfileVersion 3, 69 `@esbuild/*` platform entries). That match is what makes
`npm ci` work and removes the need for the non-reproducible `npm install`
workaround. Verified by a real build before committing.

### 3.4 Why one image works in every environment

Vite inlines `VITE_*` variables at **build** time — the same trap as `NEXT_PUBLIC_*`.
Here it costs nothing, because every `import.meta.env` use in `src/` has a runtime
fallback:

```js
import.meta.env.VITE_PUBLIC_API_BASE || window.location.origin
import.meta.env.VITE_WS_HOST          || window.location.host
```

and the backend address is injected at **container start** via `BACKEND_URL` →
`envsubst` → `nginx.conf`. So there are **no build-time environment variables and no
build-time secrets**, one image is valid everywhere, and rollback is a pure re-tag.

`.env` was already excluded by `.dockerignore` before this migration, so no `.env`
file has ever entered a build of this app.

> **Keep it this way.** If a `VITE_*` var without a runtime fallback is ever added,
> the image stops being environment-agnostic and you'd need one image per
> environment. Extend the `BACKEND_URL`/nginx pattern instead. Never put a secret
> in a `VITE_*` var — it ships to the browser.

## 4. Bugs found and fixed

Each was found by actually running things, not by reading code.

### 4.1 The healthcheck would have failed permanently

The proposed healthcheck used `http://localhost/healthz`. Run inside the container:

```
$ docker exec fe-verify wget --quiet --tries=1 --spider http://localhost/healthz
wget: can't connect to remote host: Connection refused

$ docker exec fe-verify wget --quiet --tries=1 --spider http://127.0.0.1/healthz
OK (exit 0)
```

**Cause:** `localhost` resolves to `::1` first, but nginx `listen 80` binds IPv4
only. busybox wget gets `ECONNREFUSED` and the container is marked `unhealthy`
forever. Since `deploy.sh` rolls back on an unhealthy container, **every deploy would
have rolled itself back.**

**Fix:** `http://127.0.0.1/healthz`, with the reason recorded in a comment.

### 4.2 Stale test assertion (suite was 256/257)

```js
// before — failed
expect(t.currentStatus.value).toEqual({ phase: '…', label: '…' })
// after — passes, still strict
expect(t.currentStatus.value).toEqual({ phase: '…', label: '…', reason: '' })
```

`useAgentTimeline.js` always sets `currentStatus = { phase, label, reason }`; the
test predated the `reason` field. Fixed strictly rather than loosening to
`toMatchObject`, so the assertion still catches shape drift — which is what made it
stale in the first place. Needed before CI could gate deploys on tests.

### 4.3 Production disk at 99%

Found during host inspection: 257 MB free. Would have broken the ECR pull outright.
See §7.

## 6. Decision: SSM instead of SSH

The first draft used `appleboy/ssh-action`, which requires the private key as a
GitHub secret and a security group that accepts SSH from GitHub runner IPs — in
practice `0.0.0.0/0` on port 22.

The box already had a working SSM agent (`SSMInstanceProfile`, agent `active`), so
the deploy job uses `aws ssm send-command` instead:

- No private key stored in GitHub
- **Port 22 was never opened** — the security group is untouched by this migration
- `SendCommand` is scoped to one instance and one document

### The `runuser` detail

SSM executes commands as **root**. `deploy.sh` rewrites `IMAGE_TAG` in `.deploy.env`
using `sed -i`, which replaces the file — as root that would leave `.deploy.env`
**root-owned**, silently breaking every later manual `./deploy.sh` run as `ubuntu`.

The job therefore wraps the call:

```bash
runuser -l ubuntu -c '/opt/aadml-frontend/deploy.sh <tag>'
```

Validated before use (`aws` and `docker` on PATH under a login shell, `ubuntu` in the
`docker` group), and confirmed after the first successful SSM run — `.deploy.env` is
still `ubuntu ubuntu`.

The job polls `ssm:GetCommandInvocation` rather than using
`aws ssm wait command-executed`, because that waiter gives up after ~100s while a
pull plus health gate can legitimately exceed it. It surfaces `deploy.sh`'s stdout
and stderr into the Actions log and fails the job on a non-`Success` status.

## 10. How it works now

Build and deploy are **decoupled**: pushing to main publishes an image but does not
ship it. Production changes only on an explicit trigger.

```
push to main
   → build.yml: npm ci → npm test (257) → docker buildx
   → push to ECR as <short-sha> + latest
   → STOPS. Nothing touches the server.

you trigger (git deploy / Actions UI)
   → deploy.yml → aws ssm send-command
   → EC2: runuser ubuntu → deploy.sh → ECR login → pull → up -d --no-build
   → health gate → healthy, or roll back to the previous tag
```

| Task | Command |
| --- | --- |
| Build an image (no deploy) | push to `main` |
| Deploy current `main` | `git deploy` |
| Deploy a specific build | `git deploy a84f6d2` |
| Roll back | `git deploy <previous-sha>` |
| Deploy from the box directly | `./deploy.sh <sha>` |
| What's running | `grep IMAGE_TAG /opt/aadml-frontend/.deploy.env` |
| Logs | `docker compose --env-file .deploy.env logs -f frontend` |
| Build locally (dev) | `docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build` |

`deploy.sh` waits for the container healthcheck. If the new image never turns
healthy it dumps the last 50 log lines, restores the previous tag, brings it back
up, and exits non-zero — so a bad build fails the pipeline instead of taking the
site down.

### Never do this again

```bash
docker compose up -d --build     # on the production host
```

That is what filled the disk and made deploys slow. The production compose file has
no `build:` section and `deploy.sh` passes `--no-build`, so it can't happen by
accident.

## 11. Phase 2 — decoupling deploy from push

Shipped the same day, immediately after the migration above.

### Why

The original design deployed automatically on every push to `main`. That couples
"I merged code" to "production changed", which is fine for some teams and wrong for
others — there's no window to merge work and ship it deliberately, and no way to
land several commits before a single release.

### What changed

The single workflow was split in two:

| Workflow | Trigger | Does |
| --- | --- | --- |
| `build.yml` | push to `main`, or manual | tests → builds → pushes to ECR, **stops** |
| `deploy.yml` | `workflow_dispatch` **only** | SSM → `deploy.sh <tag>` on the box |

`deploy.yml` has **no `push:` trigger at all**, so merging to main physically cannot
reach production. `build.yml` writes a job summary naming the tag it published and
the command to ship it, so the SHA never has to be hunted for in the log.

`deploy.yml` takes an optional `image_tag` input. Blank means "the short SHA of the
branch this was dispatched against" — which is what `git deploy` with no argument
means. Supplying a tag is how rollback works.

### The `git deploy` command

A git alias wrapping the GitHub CLI:

```bash
git config --global alias.deploy '!f() { gh workflow run deploy.yml -R datatrader-space/agentic-system-frontend ${1:+-f image_tag="$1"}; }; f'
```

```bash
git deploy              # ship current main
git deploy 1a5adb1      # ship/roll back to a specific build
```

Two gotchas worth recording:

- **Set the alias from Git Bash, not PowerShell.** PowerShell strips the inner
  double quotes when passing the value to `git`, storing `image_tag=$1` instead of
  `image_tag="$1"`. Harmless for SHA tags, wrong in general.
- **`gh` won't exist in terminals opened before it was installed** — including
  VS Code's integrated terminal, which inherits PATH from the VS Code process.
  Opening a new terminal *tab* doesn't help; VS Code itself must restart.

The alias is a convenience only. **Actions → Deploy to EC2 → Run workflow** does
the same thing from the browser.

### Verification

Commit `061b9d0` was pushed to `main`:

```
ECR:
  09:58   1a5adb1
  10:48   061b9d0, latest      ← published by the push

Server (immediately after the push):
  IMAGE_TAG=1a5adb1
  ...aadml-frontend:1a5adb1    Up 51 minutes (healthy)
```

The push published an image and the server **did not move** — container uptime
unchanged at 51 minutes. That is the decoupling working.

`git deploy` was then triggered, and the deploy workflow succeeded in 23s:

| | Before deploy | After deploy |
| --- | --- | --- |
| Container | `:1a5adb1`, up 51 min | `:061b9d0`, up 46s (healthy) |
| `IMAGE_TAG` | `1a5adb1` | `061b9d0` |
| Served asset | `index-gR5jF4om.js` | `index-DOZeGZDf.js` |

The changed asset hash is the proof the new build is genuinely being served rather
than a cached old one. `.deploy.env` remained `ubuntu`-owned, confirming the
`runuser` wrapper still holds. All endpoints 200, including the `/api/` proxy and
the co-hosted sztax.ca.

This was also the **first real container swap** — every earlier automated run
redeployed the tag already running, which `deploy.sh` correctly treats as a no-op.

### Known wart

`deploy.sh` writes `IMAGE_TAG` to `.deploy.env` *before* pulling. Deploying a tag
that hasn't been built yet therefore fails at the pull but leaves the file pointing
at a nonexistent image, so a later bare `./deploy.sh` on the box would retry the bad
tag. The running site is never affected.

Fix, if it becomes annoying: pass `IMAGE_TAG` as a shell env override for the pull
and `up` (shell env beats `--env-file` in Compose's precedence), and only write the
file after the health gate passes — making `.deploy.env` always record the last
*known-good* tag rather than the last *attempted* one.

## 12. Not done / possible next steps

- **Zero-downtime.** The swap is ~8s. Host nginx already fronts the container, so
  blue/green is cheap when wanted: start the new tag on a second port, flip the
  nginx upstream, remove the old container. Full ECS/ALB only becomes worth it with
  horizontal scaling and health-based auto-rollback across instances.
- **Instance size.** The t2.small is fine now that it only pulls and runs, but it
  has 1.9 GiB RAM and a 19 GB disk shared with another site. Worth watching.
- **Port binding.** The container publishes on `0.0.0.0:8002`. Since host nginx
  proxies from localhost, binding `127.0.0.1:8002` would reduce exposure. Not
  changed here to avoid disturbing a working production path.
- **Bundle size.** `dist/` is 19 MB with a 4.25 MB Monaco chunk. Already split into
  cache-friendly vendor chunks; lazy-loading Monaco would cut first paint further.
- **Backend.** This migration covered the frontend only. The backend on
  `172.31.6.43` still deploys the old way.
